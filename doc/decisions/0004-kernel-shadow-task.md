# D-004：被中断用户任务改用内核影子任务保存上下文

> 本 ADR 是提议稿，尚未取代 D-001。只有在本 ADR 被接受后，才把 D-001 标为 `superseded`。

## 背景

D-001 选择“被中断的用户态任务仍是用户态任务，中断上下文保存在该用户任务的 TCB 中”。该选择让内核在 trap 路径直接访问用户任务 TCB，扩大了跨特权级数据访问，也使内核操作与用户调度器的状态修改相互影响，是调度模块可重入的主要障碍之一。

D-001 当时否决了“创建内核影子任务”，理由是用户/内核任务类型转换、对应关系和生命周期复杂。现在考虑重新选择该方向：把中断上下文移入一个独立的内核任务，可以避免内核直接操作用户任务 TCB。

## 决策

- 被中断的用户态任务不再由内核直接在该任务的 TCB 中保存中断上下文；改为创建一个**内核影子任务**保存上下文。
- 影子任务位于内核调度器；保存期间其地址空间/pid 赋值为被中断用户任务所在进程。
- 影子任务是特殊内核任务：恢复用户上下文时使用 `krun_utask`，不使用普通 `run_task`；恢复前把 `CURRENT_TASK` 恢复为对应的用户态任务。
- 除恢复方式外，影子任务按普通内核任务管理。
- 被中断的用户态任务保持用户任务身份和 `Running` 状态；在影子任务恢复它之前，它不在任何核心上运行，也不在就绪/阻塞队列中。
- `trap_handler` 完成后是直接恢复影子任务，还是正常走调度，尚未决定（见 Q-049）；本 ADR 只确定影子任务模型。

## 替代方案

- **沿用 D-001**：用户任务 TCB 保存中断上下文，内核直接访问用户任务；可重入问题保留。
- **把用户任务转成内核任务**：类型转换和恢复后的反向转换复杂，用户任务身份会丢失。
- **正常调度影子任务**：可以获得抢占语义，但同一核心可能出现多个影子任务，需要额外的创建/销毁和对应关系管理；见 Q-049。

## 后果

- 内核不再直接操作用户任务 TCB，跨特权级访问面缩小，有利于可重入。
- 需要维护“用户任务 ↔ 内核影子任务”的对应关系、生命周期和同步。
- 用户任务被中断后可能处于 `Running` 但不在核心上运行的状态；状态机和唤醒逻辑需要覆盖该状态。
- 若采用“直接恢复”，每核心通常只需要一个影子任务，但不会实现抢占语义；若正常调度，则需要管理多个影子任务。
- Q-007 目前基于 D-001 判定；D-004 被接受后需要重新判定。
