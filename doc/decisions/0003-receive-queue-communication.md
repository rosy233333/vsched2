# D-003：通信队列改为接收队列接入调度器外部

## 背景

旧方案用**事件源**把通信队列接入调度器内部：每个事件源有请求/响应双队列，调度器查询事件源并选择任务。跨进程唤醒用户任务后，多条只负责唤醒的响应队列不再需要各自存在；调度器也不应继续承担通信队列的接入。

## 决策

- 旧方案称**事件源**，通信队列接在调度器内部。
- 新方案称**接收队列**，通信队列接在调度器外部。
- 新方案仍保留双队列角色：请求队列按通信端点；接收队列按进程共享。
- 多个只负责唤醒、没有批处理功能的响应队列，汇聚为每进程一条接收队列。
- 没有批处理需求的端点不建请求队列，直接使用共享接收队列。
- 调度器只从就绪队列取任务；目标调度循环把接收队列内容搬入就绪队列。
- 硬件队列的固定双队列接口无法改造，保留 dispatcher 轮询。

## 替代方案

- **保留事件源多组双队列**：调度器继续查询通信队列，接入位置仍在内部；否决。
- **全局单队列**：所有端点和唤醒共用一条队列，无法区分批处理与接收队列角色；否决。

## 后果

- 调度器不再维护事件源数组，职责收窄为就绪队列和调度决策。
- 接收队列需要 VVAR 中的数据布局、安全边界和生命周期设计。
- 无批处理端点只使用接收队列，通信路径更短。
- 无在线任务、无法及时搬运、无法抢占目标进程低优先级任务仍是未决项。
- 硬件队列保留 dispatcher，通信模型存在一个固定双队列例外。
