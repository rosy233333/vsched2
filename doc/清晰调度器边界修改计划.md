# 清晰调度器边界修改计划

目前，许多任务相关操作（如让出、阻塞）需要在调度器外部完成一些操作（如设置任务状态、放入阻塞队列）再进入调度器。这模糊了调度器内外的边界，扩大了接口范围，增加了操作系统适配调度器的难度，不利于调度器的移植。因此计划将尽可能多的任务相关操作移动到调度器内部进行。

## 需要移动至调度器内的操作

- （让出、阻塞、退出时的）任务状态设置，让任务状态的修改完全在调度器内进行。
  - 因此，需要在进入调度器入口时，增加任务准备执行哪种操作的信息。
- 阻塞队列的实现
  - 任务放入阻塞队列
  - 任务唤醒（从阻塞队列中取出、放入就绪队列）
    - 不在调度器的主循环中，而是作为调度器提供的，可随时调用的接口
    - 需要考虑基于Waker的协程唤醒，实现协程的Waker
- 开关中断（将中断状态作为上下文的一部分，增加对应的接口）
- 协程的让出、阻塞等接口？（由调度器提供，但并非使用vdso中的代码，而是使用与主编译单元一同编译的代码。）

## 难点

- [x] 协程进入调度入口时的信息传递
  - 协程在未执行完成时只能向调度器返回Pending，难以传递阻塞、让出还是退出的状态信息。
    - 方案：在任务接口中增加存取action字段的接口，代表下一次主动进入调度器时的行为（让出/阻塞在某条队列上/退出）。
      - 通过由调度器提供让出/阻塞/退出接口，保证除了一般Future返回Pending外，所有主动进调度器的选择都设置了action
      - 进入调度器后清除action，用于识别“一般Future返回Pending”的情况。
      - 中断/异常/系统调用等被动进调度器不会读取和修改action
  - 协程的阻塞：
    - 若与调度器内部的阻塞队列配合，则最理想的情况是协程返回Pending后再放入调度器。这就需要在协程返回时传递更多的信息。
    - 若协程调用外部的异步函数（例如例如async_std的File::read），并在外部的异步函数中阻塞，则被阻塞的协程对调度器可见，但没有使用调度器的阻塞队列，而是使用外部异步函数中的阻塞机制。
      - 必要性：我认为这样是有必要的，因为即使是调度器管理的协程，也有调用外部异步函数（例如处理文件、网络等IO操作）的需求，无法保证协程调用的（可阻塞的）异步函数只有调度器内部的阻塞API。 
      - 可行性：虽然阻塞和唤醒在外部进行，但它们都是使用协程的Waker机制实现的。只要在调度器内部提供对Waker方式阻塞的支持（例如正确地设置任务状态；在阻塞和唤醒时处理好同步问题；在调度器中定义Waker及其操作），就可以让外部的阻塞和唤醒也被调度器支持。
- [x] 线程的上下文保存
  - 当前的设计中，外部代码先保存了上下文，再进入调度器代码（即调度循环中）。但新的设计需要由调度器代码（非调度循环）实现让出、阻塞等操作，再进入调度循环，就需要调度器代码有保存线程上下文的功能。
  - 目前的计划是使用已有的resched接口（该接口原本用于实现trap_handler的阻塞）。
    - 优势：无需新增接口。
    - 不足：这样会使执行流经历调度器代码（非调度循环） -> 外部代码 -> 调度器代码（调度循环），是否太复杂？
- [x] 重要的同步问题分析
  - 阻塞-唤醒的同步（均位于调度器内）
  - 设置/检测阻塞条件-阻塞-唤醒的同步
    - 方案1：
      - `Fn() -> bool`也是一种trait，可以通过类似胖指针的方式，用两个usize的空间，既存储指针，又存储vtable。
      - 因此，可以在每条就绪队列中，以trait object指针的形式存放相应的阻塞条件。
      - 为了避免丢失唤醒，在加入阻塞队列后再检测一遍阻塞条件。
      - 该方案的不足：加入队列后再二次检查，复杂度高。
    - 方案2（目前暂时选择）：
      - 唤醒是一种通知，可以在就绪队列中缓存这种通知。
      - 通过一个`SpinLock<Isize>`存储通知数量（记为正数）/等待的任务数量（记为负数），类似于信号量。
        - 用锁而不用原子变量的原因，是为了把加入阻塞队列的过程也放入锁的临界区内。
      - 任务因条件不满足而阻塞时，将该数-1并返回原值，原值<=0则阻塞。
      - 若取消阻塞条件后可以唤醒一个任务，无论其在之前或之后到来（如互斥锁的情景），则将该数+1。
      - 若取消阻塞条件后可以唤醒所有任务，但不包括之后到来的任务，则将该数设为0。
      - 若取消阻塞条件后可以唤醒所有任务，包括之后到来的所有任务（如被join的任务退出），则将该数设为正无穷。
      - 虽然从检测通知到加入阻塞队列中间也有一段时间，可能通知在这段时间内到达从而丢失唤醒，但检测通知的时机移到了调度器内，与加入阻塞队列很近的位置。
      - 因此，可以通过加锁保护，把“检测通知-加入阻塞队列”变为原子操作。
      - 该方案的不足：以上的三种情况，不知道是否涵盖了对阻塞队列和条件阻塞的所有需求。
- [x] 协程接口的提供形式
  - 如果由vDSO内的代码提供，则形式上无法作为Future提供，也就无法存储状态。
  - 如果由与主编译单元一同编译的代码提供，则无法访问vDSO内部的变量。
  - 与主编译单元一同编译的代码提供Future形式和状态保存，vDSO内部的代码提供实际的poll函数？
    - 这样的实现方式，能不能把vDSO内外的配合直接在vsched2和vdso_crate_template中完成，无需OS代码考虑？
      - 理论可行：在vsched2中准备好数据结构（不需实现Future trait）和poll函数，通过build_vdso在生成的api库中组装成Future。
      - 限制：对应的状态数据结构不能有泛型，因为其需要作为poll函数的参数。

## 开发计划

1. 在vDSO支持库中增加组装Future接口的机制（设计详见“难点”章节的“协程接口的提供形式”）
2. 在vDSO中实现让出和退出的线程/协程接口，同时将关中断、任务状态修改、放入阻塞队列的过程改为进入调度循环后进行。
  - 需要修改任务接口，增加存取action，以及存取中断状态的接口。
3. 在vDSO中实现协程Waker，支持一般的Future的阻塞和唤醒。
4. 在vDSO中添加阻塞队列，并实现阻塞的线程/协程接口。
