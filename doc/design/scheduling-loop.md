# 调度循环与路径

> 本文件是步骤 1 的调度循环设计。路径/时序是当前文字版调度时序，图作为视觉对照；代码尚未按此实现。未决项见“未决 Q”和 [问题台账](../questions.md)。但在后续步骤2、3中会进一步修改。

## 问题/目标/非目标

**问题**：调度循环要在内核/用户、内核态/用户态、不同地址空间和不同上下文类型之间切换。需要明确每一步由谁保存、由谁选择、由谁恢复，避免内核代替用户调度器选用户任务，也避免在 VVAR 之外做不必要的跨边界访问。

**目标**：

- 覆盖“用户态任务被内核级中断打断后保存、用户调度器选择、内核恢复”的完整路径。
- 内核→用户方向，先把特权级切到用户态，再由用户调度器选择任务。
- VVAR 只共享最高优先级；进程选择在内核，用户调度器只做本进程任务选择。
- 尽量减少 VVAR 之外的跨地址空间/特权级数据操作。

**非目标**：不展开 trap 原因对应的状态机细节；不修改代码；未决项不在这里展开，见“未决 Q”。

## 模型

- **进程选择**：内核根据 VVAR 中的最高优先级选择进程/地址空间。
- **任务选择**：用户调度器（即“进程调度器”）在本进程内选择任务；这不是进程选择。
- **内核任务选择**：内核调度器选择内核任务。
- **上下文类型**：协程、线程、中断。用户任务被内核级中断打断后仍是用户任务，中断上下文在它的 TCB 中；见 [D-001](../decisions/0001-user-task-interrupt-ownership.md)。
- **特权级方向**：
  - 内核→用户：内核选进程/地址空间 → `into_user` → 用户调度器选任务。
  - 用户→内核：用户调度器选中任务后，若需要内核恢复（中断上下文）或进入内核调度，走 `into_kernel`；这是恢复/进入路径，不是让内核代替用户调度器选任务。
- **内核访问用户任务约定**：虽然用户态任务的结构可能与内核态任务不同，但为了实现以下调度路径，需要内核态OS具备访问用户态任务的上下文与状态的能力，以实现如下操作：
  - 在trap_vector中，保存用户态任务的中断上下文。
  - 在task

## 规则与不变量

- **I-01 用户任务归属**：用户态任务被内核级中断打断后仍是用户态任务，留在用户调度器；中断上下文保存在该任务 TCB。
- **I-02 内核→用户顺序**：内核先选进程/地址空间并 `into_user`，之后用户调度器才选择任务；内核不直接替用户调度器选用户任务。
- **I-03 内核任务选择**：内核任务由内核调度器选择；用户任务由用户调度器选择。`用户调度器选择内核任务`不成立。
- **I-04 优先级共享**：VVAR 只共享最高优先级；每个进程的本地优先级不放进 VVAR。进程选择在内核完成；用户调度器只读本进程私有优先级和全局最高优先级，不选择进程。
- **I-05 跨边界访问**：VVAR 之外的内核→用户任务/调度器访问必须逐项列出理由；不能解释的访问应删除或移入 VVAR/内核。
- **I-06 Trap 入口**：trap 入口保存中断上下文并做最小分类；`TrapInfo` 在入口入队；`trap_handler` 是独立任务，不合并进调度器；简单 trap 内联，复杂才新建任务。
- **I-07 中断上下文恢复**：用户调度器选中中断上下文任务后，经 `into_kernel` 进入内核恢复。
- **I-08 地址空间**：跨地址空间时，内核选进程/地址空间；进入用户态后再由用户调度器选任务。地址空间切换不等于任务选择。

## 接口影响

|---|---|---|---|

## 验证

- 用户态任务被内核级中断打断：保存到 TCB → 仍在用户调度器 → 用户调度器选中 → `into_kernel` → 内核恢复 → 返回。
- 内核→用户：内核选进程/地址空间 → `into_user` → 用户调度器选任务；内核没有替用户调度器选任务。
- 内核→内核：内核调度器选内核任务，用户调度器不参与。
- 用户调度器不参与进程选择；VVAR 只共享最高优先级。
- 跨地址空间路径：地址空间切换与任务选择分开。
- 仓库内无自动测试；实现时用场景走查 + 外部测例。
