# 通信队列：从事件源到接收队列

> 新旧方案：旧方案叫**事件源**，把通信队列接入调度器内部；新方案叫**接收队列**，把通信队列接到调度器外部。方案选型见 [D-003](../decisions/0003-receive-queue-communication.md)。

## 问题/目标/非目标

**问题**：原事件源方案把通信队列注册在调度器内部，调度器需要查询事件源、选择任务；跨进程唤醒用户任务后，多条只负责唤醒的响应队列不再需要各自存在，且调度器不应继续承担通信队列的接入。

**目标**：

- 旧方案与新方案有明确名称和接入位置对比。
- 新方案仍保留“请求队列 + 接收队列”的双队列角色，但把只负责唤醒的队列汇聚为每进程一条**接收队列**。
- 接收队列接在调度器外部，调度器只从就绪队列取任务。

**非目标**：不展开跨进程唤醒的具体机制（见 [cross-process-wake.md](cross-process-wake.md)）；不设计 trap；不实现抢占。

## 新旧方案

| 维度 | 旧：事件源 | 新：接收队列 |
|---|---|---|
| 方案名 | **事件源** | **接收队列** |
| 接入位置 | 通信队列作为事件源注册在**调度器内部**（`Scheduler.sources`） | 通信队列接在**调度器外部**；每进程一条 VVAR 接收队列 |
| 队列结构 | 每个事件源一组请求/响应双队列；多个事件源多组 | 请求队列按通信端点；接收队列按进程共享；整体仍是“请求 + 接收”双队列 |
| 唤醒队列 | 每个事件源一条响应队列；其中多条只负责唤醒 | 多条只负责唤醒的响应队列汇聚为一条接收队列 |
| 调度器职责 | 查询事件源、选择任务 | 只从就绪队列取任务；调度循环把接收队列内容搬入就绪队列 |
| 无批处理端点 | 仍保留请求/响应队列 | 不建请求队列，直接使用共享接收队列（双队列的退化情形） |

变化有两个：

1. **接收队列汇聚**：旧事件源中多条只负责唤醒、没有批处理功能的响应队列，合并成每进程一条接收队列。
2. **接入位置外移**：通信队列从调度器内部（事件源）移到调度器外部（接收队列）；调度器不再查询通信队列。

## 分析

旧双队列的作用：

1. 缓存数据，方便批处理；
2. 把唤醒操作转发到用户级任务；
3. 同时传递数据流（消息）和控制流（目标任务 id）。

跨进程唤醒用户任务并携带数据后，第 2 个作用不再需要；第 3 个作用可以由接收队列承担。因此：

- 有批处理需求的通信端点保留请求队列；
- 只负责唤醒的响应队列不再按端点保留，汇聚为进程级接收队列；
- 没有批处理需求的端点不建请求队列，只使用接收队列；
- 硬件队列有固定双队列接口，无法改造成接收队列，保留 dispatcher 轮询。

## 模型

```text
通信端点 A ──请求队列（可选，数据/批处理）──> 处理任务
                                                  │
其他端点/进程 ──wake(task, data)──> 目标进程接收队列（VVAR，按进程共享）
                                                  │
                                    目标调度循环搬入本进程就绪队列
                                                  │
                                            目标任务运行
```

- **请求队列**：按端点，只在有数据/批处理需求时存在。
- **接收队列**：按进程，放在 VVAR；承载唤醒 + 数据/控制流；不参与优先级。
- **调度器**：只消费就绪队列，不再查询事件源。

## 规则与不变量

- **I-01 接入位置**：新方案的通信队列接在调度器外部；调度器内部不再维护事件源数组。
- **I-02 接收队列汇聚**：只负责唤醒的响应队列合并为每进程一条接收队列；不按端点重复。
- **I-03 仍是双队列**：有批处理需求的端点保留“请求 + 接收”两个角色；无批处理端点只使用接收队列，是退化情形。
- **I-04 接收队列不参与优先级**：只有进入就绪队列后才按就绪队列优先级参与调度。
- **I-05 数据与控制流**：接收队列同时承载唤醒和唤醒数据；数据生命周期/所有权待定。
- **I-06 硬件队列例外**：固定双队列接口的硬件队列保留 dispatcher 轮询，不强行改造成接收队列。

## 路径/时序

1. 发送方把请求放入端点的请求队列（有批处理需求时）。
2. 处理任务处理请求；简单请求内联，复杂请求新建任务。
3. 处理结果通过 `wake(target, data)` 写入目标进程的接收队列；无请求队列的通信也直接走这一步。
4. 目标进程调度循环在安全点把接收队列内容搬入本进程就绪队列。
5. 目标任务被选中并读取数据。

## 接口影响

| 旧 | 新 | 理由 | 受影响代码 |
|---|---|---|---|
| 事件源注册在 `Scheduler.sources` | 删除事件源接入；调度器只保留就绪队列 | 通信队列移到调度器外部 | `src/schedule/` |
| 每个事件源请求/响应双队列 | 请求队列按端点 + 每进程共享接收队列 | 接收队列汇聚 | `src/schedule/`、`src/block_and_wake/` |
| 唤醒只看任务 | `wake(target, data)` | 唤醒携带数据/控制流 | `src/block_and_wake/` |
| 硬件双队列可改为事件源 | 保留 dispatcher 轮询 | 固定接口无法改造 | `src/schedule/`、驱动适配 |

## 未决 Q

- Q-041：跨进程唤醒用户任务并携带数据的完整机制（见 [cross-process-wake.md](cross-process-wake.md)）。
- Q-042：同步/异步系统调用是否共用 TrapInfo 发送队列；若共用，队列放 VVAR 的安全/所有权。
- 接收队列的容量、溢出、生命周期、安全边界；无在线任务和抢占问题。

## 验证

- 有批处理端点：请求队列 + 接收队列都工作；接收队列不参与优先级。
- 无批处理端点：只使用接收队列，不创建请求队列。
- 旧事件源不再注册；调度器只从就绪队列取任务。
- 硬件双队列仍由 dispatcher 轮询。
- 仓库内无自动测试；实现时用场景走查 + 外部测例。
