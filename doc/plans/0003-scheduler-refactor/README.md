## 步骤 1：调度循环修改

参考 [任务切换模型（0003版）](任务切换模型（0003版）.drawio)（可编辑源）；旧版 [任务切换模型（新版调度算法）](../../draft/新版设计/任务切换模型（新版调度算法）.png) 只作对照，不再作为最终源。

### 理由

1. **补全暂缺路径**：当前图/实现没有完整覆盖“用户态任务被内核级中断打断后进入内核”的保存与恢复路径；不补这条，用户态任务的中断上下文只能靠隐含路径或旧设计处理。
2. **减少跨边界数据操作**：内核直接访问用户任务或用户调度器，会扩大 VVAR 之外的共享数据和锁范围。把进程选择放到内核、任务选择放到用户调度器，并只共享最高优先级，可以缩小跨地址空间/特权级的访问面。

### 具体修改

1. **补保存/恢复路径**：用户态任务被中断时，trap 入口在内核把中断上下文保存到该用户任务 TCB；用户调度器选中该任务后，经 `into_kernel` 进入内核恢复，再返回用户任务。
2. **特权级切换前移**：把特权级切换统一放到任务选择之前。内核先选择进程/地址空间，通过 `into_user` 返回用户态，再由用户调度器在用户态选择任务；避免内核代替用户调度器选择用户任务。
3. **优先级共享收敛**：VVAR 不再共享每个进程的优先级，只共享最高优先级；进程选择统一在内核完成。用户调度器只在本进程内按优先级选择任务。

## 步骤 2：trap 机制与通信机制重构（分析/设计未完成）

本步分两部分：**修改 trap 机制**；**重构通信机制，删除事件源**。目标为**解耦通信与调度器**，因此删除事件源，让调度器只从就绪队列取任务，通信通过阻塞队列/单队列直接完成。分析/设计未完成，以下只写方向和未决问题，不写可执行步骤。

### 分析

#### 跨进程唤醒

原本的一些IPC方式（例如信号量、互斥锁）就需要阻塞队列具有跨进程唤醒线程能力。原本易于实现是因为原本的线程是内核级线程，统一归内核级调度器管理。因此，为了支持这些IPC功能，本项目的阻塞队列也需要具有跨进程唤醒用户态任务的能力。

挑战在于，本项目的任务是用户级任务，因此跨进程唤醒（在当前情况下）需要操作其它地址空间的调度器。

跨进程唤醒应该属于**调度机制**，还是属于**事件通信机制**？我认为，“把任务放入就绪队列”是调度机制向事件通信机制提供的接口。在原有的内核级线程情况，这个接口本身就能处理跨进程的情况，因此事件通信机制（如阻塞队列）只在其上做了很少的包装。阻塞队列属于事件通信机制，但“放入就绪队列”是调度机制。此外，内核级线程也有使用事件通信机制实现跨进程唤醒的情况，例如用户态中断。这是因为原本使用阻塞队列的情况需要陷入内核，开销较大而提出的替代方案。

但在我们的用户级任务的情况，原本的调度接口就无法原生支持跨进程唤醒了。我们的方案也对解决此问题有一定优势：阻塞队列也纳入了任务管理模块的范畴，因此可以调整阻塞队列的实现。

目前有讨论，应该寻找直接唤醒的**调度机制**方案，还是是通过**事件通信机制**将跨进程唤醒转化为进程间唤醒？

#### 以单队列替换事件源双队列的分析

双队列的作用体现在：

1. 缓存数据，方便批处理，而批处理就意味着用一个任务处理多条数据。
2. 将唤醒操作转发到用户级线程/协程（因为前面提到已有的唤醒操作的粒度只能达到内核级线程）。此情况下，唤醒操作成为了一种数据，由dispatcher批处理这种数据，并依次唤醒对于的用户级线程/协程。
3. 同时传递数据流（消息本身）与控制流（消息需要唤醒的任务id）

但在已经实现了跨进程唤醒用户级任务的前提下，第二个作用就不再需要了。而如果允许跨进程唤醒机制携带数据，则第三个作用也不再需要。因此，只需要在有批处理的需求时，才需要使用队列。

以IPC为例，可以把原本的双队列改为单队列：

- IPC的发送过程依然使用队列，由一个进程内的不同的用户级任务向同一个队列发送IPC消息。接收方进程使用一个handler任务依次处理这些请求（满足“批处理”需求），简单请求直接在handler任务内完成，困难请求才需要新建任务解决。（注意：如果所有请求都新建任务的话，就没有起到批处理的作用，因此也不需要队列，直接每个用户级任务唤醒对应的内核级任务即可。）
- IPC的接收过程，即为返回结果、唤醒发送方任务的过程。而通过实现的“跨进程唤醒用户级任务”机制，这个唤醒过程不需要队列也可以直接完成。只是需要改造唤醒机制，使唤醒的同时可以传递数据（IPC结果），也就是满足上文的“同时传递数据流和控制流”。

### 2.1 修改 trap 机制

- 收到 trap 后不进入调度器，直接唤醒 `trap_handler`（独立任务）。
- `TrapInfo` 队列结构不变；`trap_handler` 不整合进调度器。
- 简单 trap 在 handler 内完成；复杂 trap 才新建任务。
- handler 处理完阻塞，再进入正常调度。
- 可能让同步 trap 与异步系统调用复用一个发送队列（Q-042）；若复用，队列要放在 VVAR，所有权/安全待定。
- 未决风险：
  - 被 trap 任务可能在 handler 处理过程中已被唤醒；handler 阻塞后不一定回到原任务。
  - 内核运行带中断上下文的用户态任务的反复切换问题仍未解决。
  - 新 trap 机制保证中断后一定运行 `trap_handler`（Q-039 已关闭）。
- 已决定：`trap_handler` 不合并；`TrapInfo` 在 trap 入口入队；handler 处理简单 trap，复杂才新建任务（Q-029/Q-030 已关闭）。
- Q-004 已关闭：不删除 `TrapInfo::new_handler` / `IdleHandler`。

### 2.2 重构通信机制，删除事件源

- 无队列通信：直接 block queue block/wake，不经过事件源。
- 删除事件源：调度器只从就绪队列取任务；删除 `EventSource`/vtable/`Scheduler.sources` 接入。
- 跨进程唤醒：block queue 要能唤醒其它地址空间的用户任务；需要把目标任务放入目标用户调度器就绪队列，并携带唤醒数据。详见[2.3](#23-跨进程唤醒未决)。
- 队列只在批处理情景（即用同一个任务处理队列中的所有请求）下保留。否则直接唤醒；如果所有请求都新建任务，就没有批处理需求，也不需要队列。
- IPC：发送方用单队列，接收方 handler 批处理；简单请求内联，复杂请求新建任务；结果返回直接唤醒发送方并携带结果，不需要队列。
- 异步系统调用：类似；是否允许用户态唤醒内核任务有安全风险；批处理可避免。
- 硬件队列：固定双队列接口无法改单队列，保留 dispatcher 轮询并唤醒用户任务。
- 事件源旧 Q（Q-002/Q-023/Q-034/Q-037）已关闭。

### 2.3 跨进程唤醒（未决）

核心问题：如何跨地址空间把任务放入目标用户调度器，并携带数据，同时保证生命周期/安全/不破坏 VVAR 之外的访问约束。

暂定的方案：

每个进程在VVAR中设置任务接收队列；跨进程唤醒时将任务放入该接收队列中；在进程中的任务调度循环中将接收队列中内容搬入就绪队列中。

接收队列中的任务不影响进程优先级；只有放入就绪队列后才会通过就绪队列优先级影响进程优先级。

[以单队列替换事件源双队列的分析](#以单队列替换事件源双队列的分析)提到唤醒机制还有携带数据的需求，这也可以通过接收队列实现。

仍待定的问题：

- 如何将唤醒机制携带的数据传入任务内部
- 如果进程没有任务在线，即使放入接收队列也无法及时放入就绪队列，也就无法更新进程优先级
- 唤醒高优先级任务时，无法直接抢占其所在进程的低优先级任务

否决的方案：

- 将进程的整个就绪队列搬入VVAR（暴露面过大，有安全问题）
- 内核中介（开销大）
- 用户态中断（需硬件支持）

## 步骤 3：调度模块可重入（分析/设计未完成）

思路：**把调度模块代码也视为任务的一部分**。用户态调度代码被中断时，按“任务被中断”的路径保存嵌套现场，再由内核恢复；恢复旧现场不能回滚期间发生的唤醒/完成/退出。

开始前必须先补：

1. 分析嵌套现场的归属、发布时机、恢复顺序和容量。
2. 设计状态/action 与并发通知、执行权交接、跨特权级锁、`CURRENT_VSPACE`、栈保留/回收。
3. 明确栈保存/恢复顺序，避免同一栈被调度模块和其它核心上恢复的线程同时使用（Q-016/Q-036）。
4. 再拆实现步骤和验证。
