# 调度模块三阶段重构计划

> 当前步骤：步骤 1“调度循环修改”。顺序是依赖顺序：先让调度循环与修正后的新图一致，再重构事件源，最后实现可重入。步骤 2/3 的分析和设计尚未完成，不写可执行步骤。

## 背景与目标

- 新版设计已经画出“任务切换模型（新版调度算法）”，但图与文字设计、当前实现之间仍有不一致；先把图修对，再按图改调度循环。
- 调度循环稳定后，事件源需要按“调度与事件通信解耦”重新接入，避免通信逻辑继续渗进调度器。
- 最后实现调度模块可重入：把调度模块代码也视为任务的一部分，用嵌套现场和交接协议避免覆盖/重复/死锁。
- 非目标：本文档不补完所有 reference/design，不解决全部 Q，不在计划阶段改代码。

| 步骤 | 目标 | 前置 | 产出 | 状态 |

| 1. 调度循环修改 | 先整理并修正新图，再按图修改调度循环 | 图错误清单、图→代码映射 | 修正图 + `design/scheduling-loop` + 代码 | draft（当前） |

## 步骤 1：调度循环修改

参考 [任务切换模型（0003版）](任务切换模型（0003版）.drawio)（可编辑源）；旧版 [任务切换模型（新版调度算法）](../../draft/新版设计/任务切换模型（新版调度算法）.png) 只作对照，不再作为最终源。

### 理由

1. **补全暂缺路径**：当前图/实现没有完整覆盖“用户态任务被内核级中断打断后进入内核”的保存与恢复路径；不补这条，用户态任务的中断上下文只能靠隐含路径或旧设计处理。
2. **减少跨边界数据操作**：内核直接访问用户任务或用户调度器，会扩大 VVAR 之外的共享数据和锁范围。把进程选择放到内核、任务选择放到用户调度器，并只共享最高优先级，可以缩小跨地址空间/特权级的访问面。

### 具体修改

1. **补保存/恢复路径**：用户态任务被中断时，trap 入口在内核把中断上下文保存到该用户任务 TCB；用户调度器选中该任务后，经 `into_kernel` 进入内核恢复，再返回用户任务。
2. **特权级切换前移**：把特权级切换统一放到任务选择之前。内核先选择进程/地址空间，通过 `into_user` 返回用户态，再由用户调度器在用户态选择任务；避免内核代替用户调度器选择用户任务。
3. **优先级共享收敛**：VVAR 不再共享每个进程的优先级，只共享最高优先级；进程选择统一在内核完成。用户调度器只在本进程内按优先级选择任务。

### 1.3 修改调度循环

在 1.1/1.2 完成后，按以下变更拆低耦合子步骤；当前只列预期改动，不写占位步骤：

1. **保存路径**：补用户态任务中断上下文的 TCB 保存；检查 trap 入口、用户/内核任务分支、栈切换。
2. **恢复路径**：补用户调度器选中中断上下文任务后的 `into_kernel` 恢复；检查 `krun_utask`/`run_task` 的职责。
3. **特权级顺序**：把 `into_user` 放到用户调度器选择任务之前；去掉内核代替用户调度器选用户任务的路径。
4. **优先级/进程选择**：VVAR 只保留最高优先级；进程选择在内核完成；清理 per-process 优先级共享和跨边界访问。
5. **验证/收尾**：场景、接口表、Q 更新。

每个子步骤实现前补文档/测试/完成标准；接口变更评审通过后再动代码。

## 步骤 2：trap 机制与通信机制重构（分析/设计未完成）

本步分两部分：**修改 trap 机制**；**重构通信机制，删除事件源**。目标为**解耦通信与调度器**，因此删除事件源，让调度器只从就绪队列取任务，通信通过请求队列/接收队列完成。分析/设计未完成，以下只写方向和未决问题，不写可执行步骤。

### 分析

新旧通信方案、接收队列汇聚和接入位置变化见 [design/communication.md](../../design/communication.md)；跨进程唤醒见 [design/cross-process-wake.md](../../design/cross-process-wake.md)。这里只保留 Step 2 的执行摘要。

### 2.1 修改 trap 机制

- 收到 trap 后不进入调度器，直接唤醒 `trap_handler`（独立任务）。
- `TrapInfo` 队列结构不变；`trap_handler` 不整合进调度器。
- 简单 trap 在 handler 内完成；复杂 trap 才新建任务。
- handler 处理完阻塞，再进入正常调度。
- 可能让同步 trap 与异步系统调用复用一个发送队列（Q-042）；若复用，队列要放在 VVAR，所有权/安全待定。
- 未决风险：
  - 被 trap 任务可能在 handler 处理过程中已被唤醒；handler 阻塞后不一定回到原任务。
  - 内核运行带中断上下文的用户态任务的反复切换问题仍未解决。
  - 新 trap 机制保证中断后一定运行 `trap_handler`（Q-039 已关闭）。
- 已决定：`trap_handler` 不合并；`TrapInfo` 在 trap 入口入队；handler 处理简单 trap，复杂才新建任务（Q-029/Q-030 已关闭）。
- Q-004 已关闭：不删除 `TrapInfo::new_handler` / `IdleHandler`。

### 2.2 重构通信机制，删除事件源

- 无队列通信：直接 block queue block/wake，不经过事件源。
- 删除事件源：调度器只从就绪队列取任务；删除 `EventSource`/vtable/`Scheduler.sources` 接入。
- 跨进程唤醒：block queue 要能唤醒其它地址空间的用户任务；需要把目标任务放入目标用户调度器就绪队列，并携带唤醒数据。详见[2.3](#23-跨进程唤醒)。
- 请求队列只在批处理情景（同一个任务处理队列中的所有请求）下保留；只负责唤醒的响应队列汇聚为每进程一条接收队列；如果所有请求都新建任务，就不需要请求队列。
- IPC：发送方用请求队列，接收方 handler 批处理；简单请求内联，复杂请求新建任务；结果通过接收队列直接唤醒发送方并携带结果，不需要每端点响应队列。
- 异步系统调用：类似；是否允许用户态唤醒内核任务有安全风险；批处理可避免。
- 硬件队列：固定双队列接口，保留 dispatcher 轮询并唤醒用户任务。
- 事件源旧 Q（Q-002/Q-023/Q-034/Q-037）已关闭。

### 2.3 跨进程唤醒

问题、模型、当前方案和已有问题见 [design/cross-process-wake.md](../../design/cross-process-wake.md)；方案选型理由见该设计文档里的 D-002 链接。

当前方案摘要：每个进程在 VVAR 中设置任务接收队列；跨进程唤醒把目标任务和唤醒数据放入目标进程的接收队列；目标调度循环在安全点搬入本进程就绪队列；接收队列不影响优先级，进入就绪队列后才参与调度。

未决：唤醒数据如何传入任务内部、目标进程没有在线任务时如何搬运/更新优先级、无法抢占目标进程低优先级任务；由 Q-041/Q-042/Q-044 跟踪。

### 2.4 接口影响（待定）

| 旧 | 新 | 理由 |
|---|---|---|
| `EventSource`/`EventSourceVtable`/`Scheduler.sources` | 删除；调度器只保留就绪队列 | 调度与通信解耦 |
| `TrapWaitQueue` 作为事件源 | 保留 `TrapInfo` 队列，但不再注册为事件源 | Trap 队列不变 |
| `BlockQueue` wake | 跨进程 `wake(target, data)`；阻塞队列可在 VVAR 共享，信号量表示消息数/等待 | 唤醒用户任务并携带数据；批处理同步 |
| trap 后进入调度器 | 直接唤醒 `trap_handler`；处理完阻塞 | 简单 trap 内联 |
| 硬件双队列 | dispatcher 轮询 | 固定接口无法改造成接收队列 |

7. 硬件队列 dispatcher 边界。

相关 Q：Q-041、Q-042、Q-044；Q-022 为异步系统调用模块边界；Q-002/Q-023/Q-029/Q-030/Q-034/Q-037/Q-039/Q-043/Q-045/Q-046 已关闭。

## 步骤 3：调度模块可重入（分析/设计未完成）

思路：**把调度模块代码也视为任务的一部分**。用户态调度代码被中断时，按“任务被中断”的路径保存嵌套现场，再由内核恢复；恢复旧现场不能回滚期间发生的唤醒/完成/退出。

开始前必须先补：

1. 分析嵌套现场的归属、发布时机、恢复顺序和容量。
2. 设计状态/action 与并发通知、执行权交接、跨特权级锁、`CURRENT_VSPACE`、栈保留/回收。
3. 明确栈保存/恢复顺序，避免同一栈被调度模块和其它核心上恢复的线程同时使用（Q-016/Q-036）。
4. 再拆实现步骤和验证。

在这些完成前，不写可执行步骤；当前只登记为 blocked。相关 Q：Q-006、Q-008、Q-009、Q-010、Q-011、Q-012、Q-013、Q-014、Q-016、Q-018、Q-019、Q-036。
