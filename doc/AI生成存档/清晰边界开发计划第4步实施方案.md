# 开发计划第4步实施方案：阻塞队列与阻塞接口

对应[《清晰调度器边界修改计划》](清晰调度器边界修改计划.md)开发计划第4步：

> 4. 在vDSO中添加阻塞队列，并实现阻塞的线程/协程接口。

本方案沿用第2、3步已经落地的机制（`SchedAction`、`state_lock_acquire/release`、`resched`、`push_task`），并把“阻塞条件的检测—加入阻塞队列”从OS代码收进vDSO的调度器入口，使“检测通知 + 入队”成为一个原子操作（即计划中“难点/重要的同步问题分析”的方案2）。

本方案已按以下决策确定：

1. 阻塞队列**固定预创建**，队列号**由调度器分配**（OS不能自选id）；
2. 阻塞队列**不是调度器事件源**，唤醒时直接把任务放入就绪队列；实现放在`block_and_wake`模块下（不放在`schedule`模块下）；
3. 信号量计数约定**按流程图**（`notifications -= 1`，旧值`>0`则不阻塞，`<=0`则入队阻塞）；
4. **需要**“按任务指针定向唤醒”（`block_wake_task`）；
5. **不需要**跨地址空间唤醒；
6. `free_block_queue`要求队列为空；
7. `BLOCK_QUEUE_NUM`直接规定上限为64，不实现多字位图；
8. `block_wake_task`失败时**不降级**，是否降级由OS决定；
9. 唤醒后**不做抢占**；
10. **阻塞队列不与Waker耦合**：阻塞队列内部不使用Waker，Waker只用于“外部异步函数（如异步IO）实现的阻塞”。因此唤醒一个已挂起在阻塞队列上的任务必须使用`block_wake_task`，而不是Waker。

---

## 1. 阻塞队列的功能范围

### 1.1 定位

阻塞队列是**调度器内部**的等待/唤醒原语，不是条件变量，也不是信号量本身：

- 调度器负责：任务的挂起（入队）、唤醒（出队 + 放回就绪队列）、以及“通知—挂起”之间的同步（防止丢失唤醒）；
- OS负责：阻塞条件本身的判断与维护（如互斥锁是否可用、管道是否有数据），即“何时调用阻塞”“何时修改通知数”。

也就是说，OS只需：

1. 在“条件不满足”时调用阻塞接口（自动完成检测通知、入队、让出）；
2. 在“条件被改变”后调用唤醒接口（自动完成出队、放回就绪队列）。

OS不再需要：设置任务状态、判断任务状态、持有/传递阻塞队列锁、把任务手动放进任何队列。

### 1.2 范围内（本次实现）

| 功能 | 说明 |
| --- | --- |
| 队列数据结构 | 固定数目（`BLOCK_QUEUE_NUM`，上限64）、固定容量（`BLOCK_QUEUE_SIZE`）、无堆分配的阻塞队列，作为`Scheduler`的字段 |
| 队列号分配器 | 调度器内部的分配位图，`alloc_block_queue()`分配、`free_block_queue(id)`回收（要求队列为空）；OS只能使用分配到的id |
| 通知计数 | 每条队列一个`SpinLock<isize>`，名为`notifications`：负值=阻塞的任务数，正值=可让任务不阻塞的通知数；`检测通知`与`入阻塞队列`在同一临界区内完成 |
| 挂起（线程） | 在线程上下文中阻塞当前任务，进入`thread_entry_phase2`后由调度器入队 |
| 挂起（协程） | 以`Future`形式（`async_api!`生成）阻塞当前协程，进入`run_coroutine`后由调度器入队 |
| 唤醒一个 | 从队头取出并放回就绪队列，或将通知缓存给“之后到来”的任务 |
| 定向唤醒 | 按任务指针从队列中取出指定任务并放回就绪队列，同时把`notifications`加1（被移除的阻塞任务不再占用负数计数） |
| 唤醒全部 | 只唤醒当前等待者（`notifications = 0`）或同时放行之后到来的任务（`notifications = isize::MAX`） |
| 队列查询 | 队列指针获取、阻塞任务数查询、当前任务挂起所在队列号（调试与OS判断需要） |
| 与Waker的关系 | **无耦合**。阻塞队列不使用Waker；唤醒挂起在阻塞队列上的任务必须用`block_wake_task`。Waker（第3步）只服务于外部异步函数自己的阻塞 |

### 1.3 范围外（明确不做，留给后续步骤或OS）

| 不做的事 | 原因 |
| --- | --- |
| 条件变量、信号量、互斥锁等同步原语 | 属于OS层，只需用本步的“检测通知+入队”与“修改通知”组合实现 |
| 阻塞队列的per-CPU化与优先级分组 | 队列本身不产生“可运行任务”（唤醒直接放回就绪队列），按FIFO+容量即可；后续如有需要再扩展 |
| 把阻塞队列注册为调度器事件源 | 已确认不需要：唤醒路径直接`push_task`到就绪队列，队列自身永不产生可运行任务，也不参与`hightest_priority`计算 |
| 跨地址空间/跨特权级的唤醒 | 已确认不需要。队列位于各地址空间的`Scheduler`私有数据中，第4步只保证“在阻塞任务所属地址空间、所属特权级内阻塞与唤醒” |
| 阻塞队列与Waker的互操作 | 已确认不需要：两者定位不同（调度器阻塞 vs 外部异步函数的阻塞），OS不得用Waker唤醒挂起在阻塞队列上的任务 |
| 唤醒时主动触发调度/抢占 | 已确认不需要：唤醒只入就绪队列并更新优先级，是否切换由已有调度流程决定 |
| 让任务“阻塞在任意事件源上”（如`EventSource`作为等待对象） | 第5步及后续按需扩展 |
| trap处理任务的阻塞（`trap_wait_queue`） | 属第5步；本步实现不得复用`trap_wait_queue`的状态约定 |

### 1.4 数据结构

新增常量（`build.rs`的`mut_cfg!`）：`BLOCK_QUEUE_NUM`（队列条数，上限64，建议16）、`BLOCK_QUEUE_SIZE`（每条队列的阻塞任务容量，建议64）。

```rust
// src/block_and_wake/block_queue.rs
pub(crate) struct BlockQueues {
    /// 队列数组，id即为下标（u32取值0..BLOCK_QUEUE_NUM）
    queues: [BlockQueue; BLOCK_QUEUE_NUM],
    /// 分配位图：第i位为1表示id=i的队列已分配给OS
    ///
    /// 因为规定BLOCK_QUEUE_NUM <= 64，单个AtomicU64即可（编译期断言），不需多字位图。
    allocated: AtomicU64,
}

pub(crate) struct BlockQueue {
    /// 同时保护阻塞任务队列与通知计数：
    /// notifications 为负表示阻塞中的任务数，为正表示已缓存的通知数。
    /// 用锁而不是原子变量，是为了把“检测通知 + 加入阻塞队列”放进同一个临界区。
    state: Mutex<BlockQueueInner>,
}

struct BlockQueueInner {
    notifications: isize,
    tasks: Deque<&'static TaskVirtImpl, BLOCK_QUEUE_SIZE>,
}
```

- `BlockQueue`类型不对外暴露；对外只暴露`u32`队列号与不透明指针（`*const ()`）。
- 队列不实现`EventSource`，也不进入`Scheduler::sources`；因此不需要`init_sources`里的用户态地址翻译。
- 阻塞队列组**不作为`Scheduler`的字段**，而是作为vDSO私有数据区的全局变量：
  `src/current.rs`中的`pub(crate) static BLOCK_QUEUES: BlockQueues = BlockQueues::new();`
  因为其字段为原子变量与自旋锁，全零即初始状态，因此不需要初始化。每个地址空间、
  每个特权级各有一份拷贝。

**有关`isize::MAX`的约定**：`notifications = isize::MAX`表示“永久放行”（唤醒所有且包括之后到来的任务），此值不再随任务阻塞而递减，也不再随任务唤醒而递增。

### 1.5 接口清单

vDSO对外接口（均放入`src/api.rs`，由`build_vdso`生成API库）：

| 接口 | 形式 | 用途 |
| --- | --- | --- |
| `block_queue_count()` | 函数 | 返回`BLOCK_QUEUE_NUM`（可用id的上界） |
| `alloc_block_queue()` | 函数 | **由调度器分配**一个队列号，返回`u32`；无空闲时返回`u32::MAX` |
| `free_block_queue(id)` | 函数 | 归还队列号；**要求队列为空**（仍有阻塞任务时失败） |
| `current_block_queue_ptr(id)` | 函数 | 取得当前调度器中id对应的队列指针（不透明，`*const ()`） |
| `block_queue_len(id)` | 函数 | 查询阻塞任务数（调试/OS判断） |
| `block_async(id)` | 协程（`async_api!`） | 协程阻塞到指定队列，被唤醒后返回`()` |
| `block_self(id)` | 线程（`extern "C"`） | 线程阻塞到指定队列；返回时已被唤醒或无需阻塞 |
| `block_wake(id)` | 函数 | 唤醒一个：按通知计数规则（见§1.6），返回是否取出了任务 |
| `block_wake_task(id, task)` | 函数 | **定向唤醒**：把挂起在id队列上的`task`移出队列、`notifications += 1`并放回其就绪队列；成功返回`true`，失败返回`false`（**不降级**） |
| `block_wake_all(id)` | 函数 | 唤醒当前全部阻塞任务（`notifications = 0`） |
| `block_wake_all_including_future(id)` | 函数 | 唤醒当前及之后的所有任务（`notifications = isize::MAX`，如join语义） |
| `current_task_block_queue_id()` | 函数 | 当前任务挂起所在的队列号；未挂起返回`u32::MAX` |

内部辅助（`src/block_and_wake/block_queue.rs`）：

- `BlockQueues::alloc() -> Option<u32>` / `free(id) -> bool`（队列非空则返回`false`）/ `get(id) -> Option<&BlockQueue>`；
- `BlockQueue::block_task(&self, task: &'static TaskVirtImpl) -> bool`：**一个临界区内**完成通知计数判断与入队；返回`true`表示“取得通知、未阻塞”（调用方置`Ready`并放回就绪队列），返回`false`表示“已入队阻塞”（调用方置`Blocked`）；
  - 必须提供这种“判断+入队合一”的方法，不能把`notifications`的读改写与`push_back`拆成两次独立的加锁（否则违反§1.6第1条“检查与入队连续持锁”，会重新引入丢失唤醒）。
  - 若实现上仍拆成`try_acquire`/`park`两个方法，则必须让调用方在同一临界区内持有同一个guard依次调用（即`park`接收guard），不允许各自加锁。
- `BlockQueue::unpark_one(&self) -> Option<&'static TaskVirtImpl>`：按通知计数规则取出一个任务（或缓存通知）；
- `BlockQueue::unpark_task(&self, task) -> bool`：定向取出，成功时`notifications += 1`（见§1.6第6条）；
- `BlockQueue::notify_all(&self, including_future: bool) -> 取出的任务数`；
- `BlockQueue::len(&self) / is_empty(&self)`。

### 1.6 同步规则（按流程图，方案2）

所有状态修改都必须与通知计数的修改在同一临界区内完成，且单个操作与虚线框内的操作序列均为原子操作。约定：

1. **挂起**（调度器入口，已保存上下文；持任务状态锁，再取队列锁，顺序见§1.7）：
   - 取队列锁；
   - 若`notifications == isize::MAX`（永久放行）：不递减，判定为“取得通知、不阻塞”；
   - 否则`old = notifications`，`notifications = old - 1`；
   - `old > 0`：取得通知，不阻塞，置`Ready`并放回就绪队列，释放锁；
   - `old <= 0`：置`Blocked`，`tasks.push_back(task)`，释放锁；
   - 判断与入队必须连续持锁完成，中间不得释放，否则通知可能丢失；
   - 置`Ready`后的`push_task`在释放队列锁与任务状态锁之后调用（§1.7）。
2. **唤醒一个**：只取队列锁（不需要任务状态锁）；
   - 若`notifications == isize::MAX`（永久放行）：无阻塞任务，返回`false`；
   - 记`old = notifications`，`notifications = if notifications == isize::MAX {old} else {old + 1}`；若`old < 0`（即原本有阻塞任务），`pop_front()`取出一个任务，释放队列锁后置`Ready`并放回就绪队列并返回`true`，否则返回`false`。
   - 因为`notifications`的所有修改都在队列锁临界区内，直接用“读取+写回”即可，不需要额外的原子比较交换。
3. **唤醒全部（不含之后到来的任务）**：取队列锁 → `if notifications < 0 {notifications = 0}`，取出当前全部任务，释放队列锁后逐个置`Ready`并放回就绪队列。
4. **唤醒全部（含之后到来的任务）**：取队列锁 → `notifications = isize::MAX`，取出当前全部任务，释放队列锁后逐个置`Ready`并放回就绪队列；之后到来的任务读到`isize::MAX`，直接放行且不再递减。
5. **不变式（调试断言可用）**：`tasks`非空时`notifications < 0`；`notifications >= 0`时`tasks`必为空。
6. **定向唤醒的通知计数**：`block_wake_task`把指定任务移出阻塞队列后，`notifications += 1`（该任务不再占用负数计数，等价于“释放了一个阻塞位”）。若`notifications`已达到`isize::MAX`则不再递增；若目标任务不在队列中，返回`false`且**不修改**`notifications`、不修改任务状态、不重复入队。
7. `SchedAction::Block(id)`的语义：**“下一次主动进入调度器时，阻塞到id号队列上”**；进入调度器读取后立即清为`JustBlock`（沿用第2步）。`id`始终是调度器分配的合法队列号，没有“id=0表示未挂起”的约定。

### 1.7 锁顺序

涉及三类锁：任务状态锁（`Task::state_lock_acquire`）、阻塞队列锁（`BlockQueue::state`）、就绪队列锁（`ReadyQueue.queues[i]`）。约定（`A → B`表示可在持有`A`时获取`B`）：

```text
任务状态锁 → 阻塞队列锁 → 就绪队列锁
```

即**任务状态锁是最外层锁**，且只有“挂起路径”会形成“状态 → 队列”的嵌套；“唤醒路径”在需要队列锁之前必须先释放任务状态锁。

- **挂起路径**（调度器入口 → `push_prev_task`）：入口读取action（不清除）并置`Blocked`；`push_prev_task`在**持有任务状态锁**的情况下取该队列锁，完成“`notifications-=1` + 判断 + 入队 + 设置状态”，然后先释放队列锁、再释放状态锁。
  - 之所以要在同一临界区内完成：入口的“检测通知 + 入队”与OS的唤醒之间存在竞争窗口，只有让唤醒方无法在“检测”与“入队”之间插入，才能保证不出现“任务已放弃阻塞却被放入队列”或反之。这正是第2步保留`Blocking`状态与状态锁的目的。
  - 由于`get_action`/`set_action`本身会获取状态锁，入口必须先读取action、再进入临界区（不能在持锁时调用`get_action`）。
- **唤醒路径**：只取队列锁取出任务（并修改通知计数）→ 释放队列锁 → 置`Ready` → `push_task`（取就绪队列锁）。
  - 唤醒路径**从不**获取任何任务状态锁，因此不存在与挂起路径的锁顺序冲突；也不需要读取任务的`action`。
  - 置`Ready`时对该任务调用`set_state`：若被唤醒任务就是当前任务（`block_wake_task(当前任务)`，或单任务自我唤醒场景），不能获取自己的状态锁（OS侧`state_lock_acquire`是`Box`分配的、不可重入的实现），需先做指针比较判断并跳过状态锁；此时任务必然处于运行态，直接`push_task`回就绪队列即可。
- **队列锁与就绪队列锁**：唤醒路径在持有队列锁时只做“弹出任务”，`push_task`在释放队列锁之后调用。
- 就绪队列锁始终是叶子锁（`push_task`内部只访问`ReadyQueue`与`PROCESS_INFO_TABLE`的原子量），不存在持它就绪队列锁再取其它两把锁的路径。

### 1.8 与旧实现（vsched `WaitQueue`）的差异

旧实现由`BlockedReschedFuture::poll`在持有队列锁的情况下自行设置状态、入队、调用`resched`。新设计把“设置状态 + 入队”统一放到vDSO的调度器入口（`thread_entry_phase2`/`run_coroutine`），OS侧只见`block_self`/`block_async`，符合“把任务相关操作移入调度器”的目标；代价是队列锁不能跨越`resched`，因此以“任务状态锁 + 队列内临界区”保证原子性（第2步已有的`Blocking`状态与状态锁正是为此保留）。另外，旧实现的`WaitQueue::notify_task`不调整计数，本方案按“负值=阻塞任务数”的语义要求`unpark_task`成功后`notifications += 1`。

   - 数据结构与§1.4一致；`Mutex`用`spin::mutex::Mutex`，队列用`heapless::Deque`。
   - `BlockQueues`实现分配位图（`AtomicU64` + `const assert!(BLOCK_QUEUE_NUM <= 64)`）与`alloc/free/get`；`free`要求`is_empty()`。
   - `BlockQueue`实现`block_task`（判断+入队合一）/`unpark_one`/`unpark_task`（成功时`notifications += 1`）/`notify_all`/`len`/`is_empty`；`isize::MAX`按§1.4/§1.6的“永久放行”语义处理。
   - **不实现`EventSource`**，不引用`src/schedule/event_source.rs`；**不使用Waker**（不引用`crate::block_and_wake::waker`）。
   - 唤醒任务时通过`Scheduler::push_task`（`src/schedule/scheduler.rs:356`）入就绪队列，并复用其优先级更新逻辑；**不要**直接操作`ready_queue`字段。
   - 需要`task`指针类型`&'static TaskVirtImpl`（与`ReadyQueue`一致）。

4. **`src/schedule/scheduler.rs`（不需要修改）**
   - 阻塞队列组不放在`Scheduler`中，因此`Scheduler`无需新增字段；
   - 阻塞队列不是事件源，因此`init`/`init_sources`/`init_except_sources`均不需要改动。

5. **`src/current.rs`**
   - 新增：
     ```rust
     /// 当前进程的阻塞队列组（以及阻塞队列号的分配器），实现为非perCPU的私有数据。
     pub(crate) static BLOCK_QUEUES: BlockQueues = BlockQueues::new();
     ```
   - 不需要初始化代码：`BlockQueues`的字段为`AtomicU64`与自旋锁，全零即“没有任务阻塞、所有队列号空闲”。
   - 与`USER_SCHEDULER`一致，该变量在用户态/内核态、以及各用户进程之间相互独立。

6. **`src/block_and_wake/block_queue.rs`（新增，不要放在`src/schedule/`下）**
   - 数据结构与§1.4一致；`Mutex`用`spin::mutex::Mutex`，队列用`heapless::Deque`（定向取出用`swap_remove_front`）。
   - `BlockQueues`：分配位图（`AtomicU64` + `const assert!(BLOCK_QUEUE_NUM <= 64)`）、`alloc/free/get`（`free`要求`is_empty()`），以及给`push_prev_task`使用的
     `block_or_resume(id, task) -> bool`：在同一临界区内完成“检测通知 + 入队”，并设置任务状态（入队则`Blocked`、取得通知则`Ready`）。
   - `BlockQueue`：`block_task`/`unpark_one`/`unpark_task`（成功时`notifications += 1`）/`notify_all`/`len`/`is_empty`；`isize::MAX`按“永久放行”处理。
   - **不实现`EventSource`**，不引用`src/schedule/event_source.rs`。
   - 唤醒函数（`block_wake`/`block_wake_all`/`block_wake_task`）**不接收`Scheduler`参数**：它们在任务将要放回就绪队列时通过`extern "C" { fn push_task(..) }`调用vDSO的`push_task`接口（与`src/api.rs`中的`push_task`是同一个函数）。
   - `block_wake_task`除“取出已入队的任务”外，还处理“任务已决定阻塞但尚未入队”的窗口：此时投递一个通知（见`waker.rs`），返回`true`；否则返回`false`（**不降级**）。
   - `current_task_block_queue_id()`等查询辅助函数也放在本模块。

7. **`src/interface.rs`**
   - `Task` trait新增：
     ```rust
     /// 读取任务中暂存的action，不修改它。
     fn get_action(&self) -> SchedAction;
     ```
     Waker需要用它判断“任务阻塞在哪条阻塞队列上”。读取在任务状态锁内进行。
   - `SchedAction`增加`Clone, Copy`（便于在持锁读取action后使用）。
   - `SchedAction::Block(u32)`的文档补充“id为调度器分配的阻塞队列号”。
   - OS侧需同步实现`get_action`（与`set_action`对称：读取TCB中的action字段）。
   - 注意`get_action`内部会获取任务状态锁，因此**不能在已持有该锁的临界区内调用**。

8. **`src/api.rs`**
   - 只放vDSO的API函数（`#[unsafe(no_mangle)] pub extern "C" fn ...`）与`async_api!`所需的状态结构/poll函数；辅助函数（如“取得当前调度器”“读取action”）不放在此处。
   - 新增§1.5的接口：`block_queue_count`、`alloc_block_queue`、`free_block_queue`、`current_block_queue_ptr`、`block_queue_len`、`current_task_block_queue_id`、`block_self`、`BlockFuture`/`block_poll`/`async_api!(block_async, ...)`、`block_wake`、`block_wake_all`、`block_wake_all_including_future`、`block_wake_task`。
   - `block_self`：持状态锁设置`action = Block(id)`与`TaskState::Blocking`后**释放状态锁**，保存中断状态、调用`resched()`，返回后恢复中断状态。
   - `block_poll`：`parked`为`true`则返回`Ready`；否则同上设置action/状态后返回`Pending`，由调度器入口完成后续处理。

9. **`src/main_loop.rs`**
   - `thread_entry_phase2`与`run_coroutine`：改为**读取**（不清除）action并分派：
     - `JustBlock`：不进入阻塞队列，置`Blocked`（协程）或直接清除action（线程：已被Waker提前唤醒）；
     - `Yield`：清除action、置`Ready`、`push_prev_task(TaskState::Ready, None)`；
     - `Block(id)`：置`Blocked`后调用`push_prev_task(TaskState::Blocked, Some(id))`，**action保持为`Block(id)`**，供阻塞窗口检测使用；
     - `Exit`：清除action、置`Exited`、`push_prev_task(TaskState::Exited, None)`。
   - `get_action`不能在持有状态锁时调用，因此入口先读取action、再进入临界区。
   - `push_prev_task`恢复`wait_queue_id: Option<u32>`参数，并在`TaskState::Blocked`分支中：
     - 持任务状态锁调用`BLOCK_QUEUES.block_or_resume(id, task)`（同一临界区内完成“检测通知 + 入队 + 设置状态”）；
     - 若取得通知（返回`false`），再以`push_prev_task(TaskState::Ready, None)`放回就绪队列。

10. **`src/block_and_wake/waker.rs`**
    - `wakeup_task`先持状态锁读取`state`与`get_action()`，释放后按结论处理：
      - `Blocking | Blocked` + `Block(id)`：调用`block_queue::block_wake_task(id, task)`，覆盖“已入队”与“尚未入队”两种情形；
      - `Blocked` + 非`Block`：第3步行为（置`Ready` + `push_task`）；
      - `Blocking`/`Running`：置`action = Yield`（令调度器入口把任务放回就绪队列）；唤醒自己时跳过状态锁；
      - `Ready`/`Exited`：忽略（冗余唤醒），不再`panic!`。

### 2.3 流程小结（线程阻塞为例）

```text
OS: 条件不满足 → block_self(id)
  → 持任务状态锁：set_action(Block(id))、state=Blocking，随后释放该锁
  → 保存中断状态/关中断 → current.resched()
调度器入口 thread_entry_phase2（持任务状态锁）:
  → set_action(JustBlock) 读取并清除action
  → 在状态锁内取队列锁，调用 block_task()（判断+入队合一）
      取得通知 → 释放两把锁 → state=Ready → 放回就绪队列
      已入队   → state=Blocked → 释放两把锁
  → 返回调度循环
其他任务: 条件改变 → block_wake(id) / block_wake_task(id, task) / block_wake_all(...)
  → 取队列锁按§1.6第2/3/4/6条取出任务（并调整 notifications），释放队列锁
  → 被唤醒任务: state=Ready → push_task 放回就绪队列
```

协程仅在“关中断/恢复中断状态的时机”和“以`Future`形式返回`Pending`”上不同（流程图已说明）。

## 3. 其他需要注意的问题

1. **`free_block_queue`失败的处理**：队列非空时`free_block_queue`返回`false`；OS应保证不再有任务挂起后再归还。
2. **`isize::MAX`（永久放行）的语义**：仅由`block_wake_all_including_future`设置；设置后不再随任务阻塞递减、也不随唤醒递增，因此不会被“新的阻塞请求”消耗掉。若要重新允许阻塞，需由OS显式调用`block_wake_all`——注意其规则是`notifications < 0`时才置0，因此永久放行状态不会被`block_wake_all`清除；如需清除永久放行，需要另加接口或由OS避免混用。
3. **OS侧使用约定（重要）**：挂起在阻塞队列上的任务只能用`block_wake*`系列接口唤醒，**不得**把该任务的Waker交给外部代码再调用`wake`；否则任务会同时进入就绪队列且仍留在阻塞队列中（重复唤醒）。
4. **不抢占**：唤醒只放回就绪队列并更新优先级（与`push_task`一致），不发送IPI、不立即切换；若后续需要“唤醒即抢占”，另开一项（与`wfi`计划相关）。

## 4. 验证方式

1. **编译**：
   - `cd ../vdso_builder && CPU_NUM=4 cargo run`（见[编译命令](编译命令.md)）。注意：直接在`vsched2`目录下用宿主目标执行`cargo check --features vdso_only`会因`src/arch/mod.rs`只提供裸机目标实现而报`unresolved imports crate::arch::assert_disable_irq / wait_irqs`，属预期现象，需用真实的裸机目标（如`riscv64gc-unknown-none-elf`）或走`vdso_builder`流程。
   - 本步完成后，`main_loop.rs`中阻塞相关的`todo!()`必须清零；`Task` trait不新增方法，OS侧无需改动。
2. **同步正确性用例**（建议先在内核态单核跑通，再上多核）：
   - 单任务自阻塞自唤醒（`block_self`前先`block_wake`缓存通知）：不应丢失唤醒；
   - “通知早于阻塞”与“阻塞早于通知”两种顺序：结果一致；
   - 两个任务争用一条队列，`block_wake`只唤醒一个（`notifications`从-2变为-1）；
   - `block_wake_all`只唤醒当前等待者（`notifications=0`），之后到达的任务仍需等待；
   - `block_wake_all_including_future`（`notifications=isize::MAX`）后到达的任务可直接通过且不被消耗；
   - `block_wake_task`：目标在队列中（成功，`notifications`加1，其余等待者不受影响）、目标不在队列中（返回`false`且不修改计数/状态）、目标是当前任务（跳过状态锁、不重复入队）；
   - 不变式断言（§1.6第5条）在所有用例中成立；
   - 唤醒方与阻塞方在不同CPU上同时进行：入队与出队不重复、不遗漏（可加计数器断言）。
3. **队列号分配**：分配`BLOCK_QUEUE_NUM`次后`alloc_block_queue`应返回“无空闲”；`free`后可复用；队列非空时`free_block_queue`应失败；越界/未分配id的查询与唤醒接口应安全失败。
4. **回归**：`yield_now`/`yield_now_async`/`exit`/`exit_async`与第3步的Waker（外部异步函数的阻塞）保持原有行为；`trap_handler`流程（第5步前）不受影响——阻塞队列不得复用`trap_wait_queue`的状态约定。
5. **接口核对**：`api.rs`中的新接口需满足`build_vdso`的正则要求（`#[unsafe(no_mangle)] pub extern "C" fn ...`、`async_api!`三个参数、`BlockFuture::new`参数中使用的类型可在API库中解析）；`init_vtable_Task`的参数个数保持不变。
